# Жизненный цикл сущностей в U-On.Travel

Понимание потока данных = понимание API. Ниже — как клиент идёт от первого касания до оплаченного тура.

---

## Полный путь

```
┌─────────────┐
│   Source    │  Источник: Instagram, сайт, Telegram, рекомендация
└──────┬──────┘
       │ заявка с сайта / звонок / сообщение
       ▼
┌─────────────┐
│    Lead     │  Обращение — клиент проявил интерес
│  (status:   │  status: Новый → Думает → Предложение отправлено → …
│   Новый)    │
└──────┬──────┘
       │ конверсия (lead → request)
       ▼
┌─────────────┐
│   Request   │  Заявка — реальный тур
│ (status:    │  status: Новая → В работе → Подтверждена → Документы готовы
│  Новая)     │           → Документы выданы → Заявка закрыта
└──┬───┬───┬──┘                                       или → Отказ / Аннулирована
   │   │   │
   │   │   └─────┐
   │   │         ▼
   │   │   ┌──────────┐
   │   │   │ Service  │  Услуги: отель, авиа, страховка, виза, питание
   │   │   │ price=X  │  type_id: 1=отель, 2=трансфер, 3=экскурсия...
   │   │   └──────────┘
   │   │
   │   └─────────┐
   │             ▼
   │       ┌──────────┐
   │       │ Tourist  │  Туристы — конкретные люди в туре
   │       │  (User)  │  Могут быть = клиент или другие (дети, супруг)
   │       └──────────┘
   │
   └─────────────┐
                 ▼
           ┌──────────┐
           │ Payment  │  Платежи — приходы (cio_id=1) или расходы (cio_id=2)
           │ price=Y  │  type_id: 1=с клиентами, 2=с партнёрами
           └──────────┘                                         │
                       ┌────────────────────────────────────────┘
                       ▼
                 ┌──────────┐
                 │  PayDoc  │  Счета внутри платежей (фискальные документы)
                 └──────────┘
```

## Что важно понять

### 1. Lead ≠ Request

**Lead (обращение)** — заявка ДО конверсии. Часто без точной даты тура, без услуг. Менеджер на этой стадии понимает «горячий или холодный».

**Request (заявка)** — реальный тур со всеми атрибутами. Имеет даты `r_dat_begin`/`r_dat_end`, туристов, услуги, платежи.

Один lead обычно конвертируется в один request. Но бывает что lead отказывается → закрывается без request.

В U-On lead может быть превращён в request через интерфейс CRM. Через API — создаём request отдельно и в lead указываем что он сконвертирован (`status_id=9` = «Заявка → Лид» — обратная конверсия, для случаев когда заявку откатывают обратно в обращение).

### 2. Туристы — это users

В U-On все физлица (клиенты, туристы) живут в одной таблице `user`. Это и заказчик (тот кто платит), и пассажиры (те кто летит).

**Привязка к заявке:**
- `r_cl_id` — кто заказчик (заплатит). Указывается при `request/create` или `request/update`.
- `tourists-requests` — кто едет. Может быть тот же заказчик + дети, супруг, друзья.

Один турист может быть привязан к множеству заявок (повторные клиенты).

### 3. Услуги (services) внутри заявки

Заявка ≠ услуга. Заявка = контейнер. Услуги добавляются по одной:

- Отель (`type_id=1`) с полями `hotel`, `city`, `country` (строки)
- Авиа (`type_id` см. справочник)
- Страховка, виза, питание, экскурсия, трансфер

Каждая услуга имеет:
- `price` — цена клиенту
- `price_netto` — закупочная (для расчёта маржи)
- `currency_id` — валюта
- `date_begin` / `date_end` — даты услуги

Суммарная стоимость заявки = сумма `price` всех её услуг.

### 4. Платежи

Платежи привязаны к заявке (`r_id`), а не к услугам. Один платёж может покрывать несколько услуг сразу.

Поля платежа:
- `r_id` — на какую заявку
- `client_id` — кто платит
- `cio_id` — приход (1) или расход (2)
- `type_id` — 1 (с клиентами) или 2 (с партнёрами)
- `price` — сумма
- `form_id` — форма оплаты (1=нал, 2=безнал, 3=карта, 4=терминал, 5=сертификат)

Заявка считается **полностью оплаченной** когда сумма приходов (cio_id=1) ≥ сумма всех её услуг.

`status_pay_id` обновляется автоматически при создании платежей:
- `1` — Не оплачена
- `2` — Частично оплачена  
- `3` — Полностью оплачена

### 5. PayDoc — фискальные документы внутри платежа

Когда нужен документ (счёт, акт, чек) — создаём `paydoc` внутри платежа. Это для бухгалтерии и фискализации (если у клиента интеграция с ОФД).

### 6. Дедлайны оплаты

Если заявка с рассрочкой — добавляются `deadlines`:
- Дата, к которой должна быть внесена сумма
- `summ` (либо `percent` от заявки)
- `is_current=1` — текущий приоритетный дедлайн
- При наступлении даты — фоновая логика U-On шлёт уведомление туристу/менеджеру

### 7. Касания (actions)

Любое взаимодействие с клиентом — `request-action`:
- `type_id=0` — комментарий
- `type_id=1` — звонок
- `type_id=2` — письмо
- `type_id=3` — встреча

Хранится в timeline заявки или в карточке туриста. Используется для отчётов «сколько касаний до конверсии».

### 8. Источники

Каждый lead имеет `source_id` — откуда пришёл. Источники настраиваются в кабинете: «Сайт», «Instagram», «Рекомендация», «Холодный звонок»...

Для UTM: `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` записываются в lead отдельно.

### 9. Статусы — мутабельны

Статусы заявок и обращений можно переименовывать, добавлять новые. У каждого кабинета свой набор.

**Стандартные флаги** работают независимо от имени:
- `is_archive` — статус «архив», не активная воронка
- `is_cancel` — отказной
- `is_confirmed` — подтверждённый (клиент сказал «да»)

Для BI группируем именно по флагам, а не по `name` — иначе при ребрендинге CRM-настроек метрики ломаются.

## Минимальный create-flow через API

```bash
# 1. Создать клиента (или найти существующего)
CLIENT_ID=$(uon users find --phone +79991234567 | jq -r '.users[0].u_id')
if [[ -z "$CLIENT_ID" || "$CLIENT_ID" == "null" ]]; then
    CLIENT_ID=$(uon users create --name Иван --surname Иванов --phone +79991234567 | jq -r '.id')
fi

# 2. Создать заявку с клиентом
REQUEST_ID=$(uon requests create --client-id $CLIENT_ID \
    --date-begin "2026-07-01 00:00:00" --date-end "2026-07-08 00:00:00" \
    --source-id 1 --note "Хочет в Турцию all-inclusive" | jq -r '.id')

# 3. Добавить услугу-отель
uon services add --request-id $REQUEST_ID --type 1 \
    --name "Hilton Resort 5*" --price-client 80000 --price-netto 65000 \
    --hotel "Hilton Resort" --city "Анталия" --country "Турция" \
    --tourists-count 2 \
    --date-begin "2026-07-01 00:00:00" --date-end "2026-07-08 00:00:00"

# 4. Привязать туриста (клиент = один из туристов)
uon tourists-requests add --request-id $REQUEST_ID --tourist-id $CLIENT_ID

# 5. Создать предоплату 30000 руб
uon payments create --request-id $REQUEST_ID --tourist-id $CLIENT_ID \
    --amount 30000 --form-id 1 --direction in --prepay-id 1 \
    --note "Предоплата"

# 6. Поставить дедлайн на доплату
uon deadlines create --request-id $REQUEST_ID --amount 50000 \
    --date "2026-06-15" --current

# 7. Поставить напоминание перезвонить
uon reminders create --request-id $REQUEST_ID --text "Перезвонить уточнить детали" \
    --from "2026-05-30 11:00:00" --to "2026-05-30 11:30:00"

# 8. Когда клиент подтвердил → меняем статус заявки на "Подтверждена"
uon requests update $REQUEST_ID --status-id 2
```

Это типичный сценарий для турагента, который завёл нового клиента и оформил тур.
