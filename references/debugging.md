# Отладка интеграции через логи U-On.Travel

У U-On в кабинете есть встроенные логи всех системных событий. Когда что-то идёт не так — это первое место, куда смотреть. API эти логи не отдаёт, только UI.

URL логов привязан к поддомену кабинета (`idXXXXX.u-on.ru`).

---

## 1. Логи: API

**URL:** `https://idXXXXX.u-on.ru/logs_api.php`

Что показывает:
- Все входящие HTTP-запросы с вашим API-ключом
- Метод, URL, time
- Тело запроса (что отправили)
- HTTP-статус ответа U-On
- Иногда — расшифровка ошибки от U-On

Когда смотреть:
- `result: 200, id: "..."` от U-On есть, но в кабинете данные не обновились → проверить, какое поле система реально записала
- HTTP 404 / 422 → видно конкретное сообщение
- Понять, почему «работает у меня в curl, не работает в скилле»
- Аудит: кто и когда дёргал API (для безопасности после ротации ключа)

Совет: при разработке держать вкладку с логами открытой в браузере и обновлять после каждого вызова. Часто проще, чем читать `references/conventions.md`.

---

## 2. Логи: WebHooks

**URL:** `https://idXXXXX.u-on.ru/logs_webhooks.php`

Что показывает:
- Все исходящие webhook-вызовы с U-On на ваш receiver
- type_id, datetime, target URL
- Полный payload, который ушёл
- HTTP-статус ответа receiver-а
- Тело ответа receiver-а (если есть)
- Retry-логика (U-On переотправляет при HTTP 5xx)

Когда смотреть:
- Receiver не реагирует → проверить, доходит ли вообще
- Нужно посмотреть точный формат payload для конкретного type_id (вместо `references/webhook-events.md`)
- Дебаг подписи / валидации на стороне receiver-а
- При первой регистрации `register-all-webhooks.sh` — проверить, что все 69 типов прилетают корректно

Совет: до прода триггернуть каждое событие вручную (создать заявку/платёж/смену статуса в кабинете) и сверить с логом.

---

## 3. Логи: онлайн-оплата

**URL:** `https://idXXXXX.u-on.ru/logs_payment.php`

Что показывает:
- Все вызовы платёжных провайдеров (Сбер, Тинькофф, ЮKassa, Точка, Альфа)
- Запросы на эквайринг, ответы, статусы транзакций
- Webhook-и о смене статусов от провайдеров

Когда смотреть:
- «Деньги пришли — статус заявки не обновился» → ищем там callback от провайдера
- Интеграция эквайринга — где упало
- Возвраты / отмены

---

## 4. Логи: онлайн-чат

**URL:** `https://idXXXXX.u-on.ru/logs_chat.php`

Что показывает:
- Сообщения из встроенного чата CRM (между менеджером и туристом)
- Интеграции с мессенджерами (TG, VK, WA, Viber, IG)
- Какие сообщения пришли из соцсетей и как U-On их распарсил

Когда смотреть:
- Сообщения из мессенджера не доезжают до карточки заявки
- Дубли сообщений
- Аудит переписки

---

## 5. Логи: SMS-сервисы

URL см. в боковом меню кабинета U-On (точный путь зависит от версии).

Что показывает:
- Отправленные SMS и статусы доставки
- Какой провайдер был использован (SMSC, SMS.RU, Beeline...)
- Стоимость каждого SMS

Когда смотреть:
- SMS-уведомления не приходят клиентам
- Расход кредитов выше ожидаемого
- Лимиты от провайдера

---

## 6. Логи: IP-телефония

URL см. в боковом меню кабинета U-On.

Что показывает:
- Все звонки из интеграции (Mango, UIS, Sipuni, Asterisk)
- Запись разговоров, длительность, тип (входящий/исходящий)
- Связь звонка с заявкой/туристом (по совпадению номера)

Когда смотреть:
- Звонки не привязываются к туристу автоматически (проблема в нормализации номера)
- Записи разговоров не доступны через API
- Кросс-проверка с `uon calls list`

## 7. Логи: уведомления в браузер

URL см. в боковом меню кабинета U-On.

Что показывает:
- Push-уведомления, которые U-On отправил менеджерам
- Время доставки, прочитал ли менеджер

Когда смотреть:
- Менеджер не видит важных событий → проверить, доставлено ли уведомление
- Дебаг `notification/create` через API

---

## 8. Логи: Письма с номерами брони

URL см. в боковом меню кабинета U-On.

Что показывает:
- Письма от туроператоров (Pegas, Coral, Anex, ...), приходящие на специальный почтовый ящик кабинета
- Распарсенные номера брони, статусы туров от ТО
- Связь с заявкой по reservation_number

Когда смотреть:
- Тур-оператор поменял статус — в U-On не отразилось
- Webhook `type_id=37` («Получение письма от туроператора по номеру брони») не сработал
- Дебаг автоматики «ТО прислал ваучер → меняем статус заявки на Документы готовы»

## Общий чек-лист «что-то пошло не так»

1. **Запрос дошёл до U-On?** → Логи API. Если нет — проверить ключ, IP-whitelist, флаги POST/GET.
2. **U-On принял?** → result в логах. Если 4xx — message указывает, чего не хватает.
3. **Запись попала в кабинет?** → result 200, но в кабинете не видно → значит U-On сохранил под другим полем или с дефолтом. Возможный мисматч поля create vs update — см. `references/conventions.md`.
4. **Webhook ушёл к нам?** → Логи WebHooks. Если нет — проверить, зарегистрирован ли в `uon webhooks list`.
5. **Наш receiver ответил OK?** → Логи WebHooks показывают статус ответа. Если 5xx — U-On будет ретраить.

Один проход по этому чек-листу — обычно достаточно, чтобы локализовать любой 90%-й баг.
